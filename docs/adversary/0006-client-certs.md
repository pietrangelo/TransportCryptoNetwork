# Adversary review 0006: short-lived client certificates (Phase 6)

**Surface:** certificate format and signature (`CertBody`, `sign_certificate`,
`verify_certificate`, signing context, canonical keys), transport in Noise message 1,
order of checks (PROTOCOL §15.4) on relay and agent, whitelist precedence and effective
scope (§15.5), time and expiry within a session (§15.6, §15.7), denylist and reload with `SIGHUP`
(§15.8), `[[authorities]]` and CA rotation (§15.9), audit (§15.11), limits (§15.12), the
`zt-ca` CLI (`keygen`, `sign`, `inspect`, issuance log) and `zt-client`'s local
checks.
**Reviewer:** independent adversary agent, given the code and not the author's
conclusions. It worked on a copy of the repository; every hypothesis was
verified with a test (prefix `adv6_`) that asserted the attackable behaviour.
**Attacker:** (a) remote host without credentials, sending arbitrary messages 1; (b) client
with a stolen key or with someone else's certificate; (c) one compromised relay out of N, which
sees and alters the traffic towards the agent; (d) operator error (wrong key in a
file, partial rollout, swapped `zt-ca` arguments).

## Findings open at review time, all fixed in this PR

| # | Attack hypothesis | Severity | Fix | Regression |
| :-: | :- | :-: | :- | :- |
| 6-1 | In the agent's `clients.toml` the key of an `[[authorities]]` entry can, by mistake, be the public key of a relay pinned with `--relay-key`: loading accepts it (only the agent's key and the whitelist were checked). A compromised relay turns its own node seed into a CA file (the `tcn-ca-secret-v1:` prefix is enough) and signs certificates that the agent admits. | medium | The agent rejects, at start-up and on every `SIGHUP`, a CA whose fingerprint is that of a `--relay-key` or of its own key, current or previous: `reject_own_key_as_authority` has become a list of forbidden keys (`reject_infrastructure_keys_as_authority`, `own_keys`), with the explicit error "authority key equals the relay key". On the relay the symmetric check already existed (a CA is never the key of an agent or a client in the policy). PROTOCOL §15.9, OPERATIONS §10.2. | `an_authority_equal_to_a_relay_or_own_key_is_refused`, `a_ca_key_equal_to_a_pinned_relay_key_is_refused_at_start_and_on_reload` |
| 6-2 | Reloading the relay keys with `SIGHUP` accepted a new key equal to a pinned CA (at start-up it was rejected). From then on every reload of the policy, and therefore of the denylist, failed with a misleading error: an urgent revocation could not get in. | low | The key reload compares the new key with the CAs of the policy in effect **and** of the one on disk (policy and keys are reloaded in two tasks on the same `SIGHUP`: a CA and an equal key written together do not both get in) and fails with `relay_keys_reload_failed` and "authority key equals the relay key"; the previous keys remain. The policy is compared only with the keys in effect, so a wrong key file does not block a revocation. | `a_relay_key_reload_equal_to_a_pinned_ca_key_is_refused` |
| 6-3 | `authentication_failed` for a certificate signed by a pinned CA but rejected after the signature check (`serial_revoked`, `expired`, `node_out_of_scope`, ...) did not report `ca` and `serial`, required by §15.11: the rejection of a revoked certificate could not be linked to the issuance log. | low | `DomainEvent::AuthenticationFailed` has the `certificate` field, populated only for the checks after signature verification (`CertRejection::after_signature`, steps 7–12), never for an unverified certificate. Relay (network task and relay core) and agent log `ca`, `serial`, `cert_name` and `not_after`. PROTOCOL §15.11, OPERATIONS §6. | `authentication_failed_after_the_signature_names_ca_and_serial`, `authentication_failed_after_the_signature_names_ca_and_serial_in_json` |
| 6-4 | The operator adds to the relay whitelist the key of a client already connected with a certificate, with a narrower `allow`, to restrict it (the whitelist takes precedence, §15.5). The open connection kept the certificate's permissions: streams and new `Open`s towards nodes no longer granted went through, whereas a new connection had the whitelist's permissions. | low | In the relay core, on every reload, if admission now yields the whitelist `Key` credential, the connection switches to `Key` and its streams are re-filtered with the whitelist's scope: the lost ones are closed with `Close Unauthorized` and `access_revoked`, as for any narrowing; from then on the connection no longer expires with the certificate. PROTOCOL §15.5. | `whitelisting_a_certified_connection_applies_the_whitelist_scope` |
| 6-5 | `zt-ca sign --log` equal to `--ca` (or a symbolic link to the key): `zt-ca` loaded the key and then appended the log line to it; the CA could no longer be loaded. | low | The log is opened with `O_NOFOLLOW`; a log with the same device and inode as `--ca` (including a hard link) and a file that starts with `tcn-ca-secret-v1:` (a copy of the key) are rejected. No certificate is created. OPERATIONS §10.3. | `an_issuance_log_that_is_the_ca_key_is_refused` |
| 6-6 | `--subject` with the client's **secret**: `zt-client keygen` writes 64 hexadecimal characters, like a public key, and if those 32 bytes are a valid point `zt-ca` signs; the secret ends up in a `0644` certificate meant to be handed out, and in the log. | low | `zt-client` rejects, before connecting and in `zt-client certificate`, a certificate whose `subject_key` is its own secret seed ("secret key leaked into a certificate: regenerate the client key"), without ever printing the secret (`Identity::is_own_secret`). OPERATIONS §10.3: `--subject` takes the `public_key` line, and what to do if the secret has ended up in a certificate. | `a_certificate_carrying_the_client_secret_is_refused` |
| 6-7 | Partial rollout: a client still in the whitelist receives a certificate before a relay or an agent pins the CA. The presented certificate is always verified and gets rejected (`unknown_authority`): the client, so far admitted by key, is locked out. | low (docs) | **Accepted** (fail closed) and documented: OPERATIONS §10.4 asks to pin the CA on all relays and agents, and to check `authorities_in_use`, before handing out certificates. | `a_certificate_from_an_unpinned_ca_is_refused_even_for_a_whitelisted_client` |

Open decision, not changed in this PR: `zt-ca` stays in the release tarball alongside
the other binaries (it is needed only on the CA machine, OPERATIONS §10.1).

## Refuted or accepted hypotheses

| # | Attack hypothesis | Outcome |
| :-: | :- | :- |
| 8 | Compromised or outdated relay that admits the client from the whitelist (with no in-session expiry): the certified session survives `not_after` | **Refuted.** The agent closes on its own at expiry (`Close Unauthorized`, `certificate_expired`). `the_agent_alone_cuts_a_certified_session_at_not_after`. |
| 9 | Bypass the denylist with the serial in uppercase or with the `-P` key | **Refuted.** Both revoke. `uppercase_serials_and_negated_keys_still_revoke`. |
| 10 | Two `[[authorities]]` (or two keys of the same entry) with `P` and `-P` to get two scopes with the same CA | **Refuted.** Rejected at load time. `authorities_with_p_and_minus_p_are_refused`. |
| 11 | Once the old key is removed after a CA rotation, its certificates are still valid thanks to the name | **Refuted.** `unknown_authority`. `removing_the_old_ca_key_invalidates_its_certificates`. |
| 12 | Responder CPU with the largest accepted message 1 | **Accepted.** In release: `respond` 132 µs, certificate not bound to the key +19 µs, bound with a forged signature +75 µs (≈ ×1.57): at most one extra signature verification per handshake, already limited by the handshake gate (§15.12). |
| 13 | Stolen certificate with another static key, malleable signatures, non-canonical or weak keys, `ca_key = -P`, signature without the context string | **Refuted** by existing tests: `a_stolen_certificate_with_another_key_never_gets_msg2`, `a_malleated_signature_is_rejected`, `non_canonical_or_small_order_keys_are_rejected`, `the_ca_key_must_match_a_pin_byte_for_byte`, `a_signature_without_the_context_string_is_rejected`. |
| 14 | Huge or garbage message 1, compromised relay that substitutes the certificate or opens out-of-scope nodes, replay to falsify the audit | **Refuted:** `garbage_or_oversized_msg1_payloads_get_no_msg2`, `a_compromised_relay_cannot_substitute_a_certificate_toward_the_agent`, `a_compromised_relay_cannot_open_a_node_outside_the_certificate_scope`, `replaying_a_certified_msg1_logs_no_session`. |
| 15 | Skew tolerance on `not_after` too, extreme times (overflow), expiry on the monotonic clock instead of the system clock | **Refuted:** `validity_has_skew_only_on_not_before`, `extreme_times_never_overflow`, `expiry_follows_wall_time_not_monotonic_time`, `a_certified_connection_closes_at_not_after`. |
| 16 | Non-atomic reload of policy and denylist, missing denylist treated as empty, hot revocation, CA equal to the process key at start-up | **Refuted:** `a_bad_revocation_file_on_reload_keeps_both_previous_files`, `authorities_require_a_revocation_list`, `sighup_reloads_revocations_and_cuts_a_revoked_certificate`, `a_ca_key_equal_to_the_process_key_refuses_to_start`. |
| 17 | Scope beyond the CA's `allow`, CA of another department, certificate for an agent key, names that authorise | **Refuted:** `a_certificate_cannot_grant_nodes_of_another_authority`, `narrowing_the_authority_allow_closes_only_the_lost_streams`, `a_certificate_for_an_agent_key_is_refused_in_the_core`, `certificate_names_never_affect_authorization`. |
| 18 | Secrets in logs and errors | **Refuted:** `a_ca_secret_pasted_into_a_trust_file_is_not_echoed`, `errors_never_print_secret_material`, `ca_signing_key_debug_is_redacted`. |
| 19 | Failover across multiple relays past a relay that does not pin the CA | **Refuted:** `a_certified_client_falls_back_past_a_relay_without_the_authority`. |
